## Step 0: 범위 검토

기존 계획은 검색 결과 전체 선택·별도 상세 화면·새 모델과 작업 클래스를 포함해 8개 이상의 파일과 2개 이상의 클래스가 예상되어 복잡도 기준을 넘음. 사용자가 핵심 범위로 축소하는 1A를 선택함.

안전한 발송 기록과 테스트까지 포함하면 여전히 여러 파일이 필요하다. 파일 수만 줄이려고 컨트롤러에 전송·작업 상태 로직을 몰아넣지 않는다. 범용 캠페인 시스템이나 독립 큐 프레임워크는 만들지 않는다. 새 작업 클래스는 한 종류를 기본으로 하고, 저장 모델은 필요한 만큼만 추가한다.

## 데이터 흐름과 상태

```text
관리자: 개별 / 등록자 전체 선택
  -> 입력·관리자 권한·알림 종류·설정·입장 링크 검증
  -> 현재 선택 대상 조회, 번호 정규화·검증·중복 제거
  -> 확인용 대상·내용 저장 (아직 발송 안 함)
  -> 대상 수 / 실제 번호 수 / 제외 / 이전 요청 이력 확인
  -> 최종 확인: 변경·만료·동시 작업 검사
  -> 명단·내용 확정 + 번호별 작업을 DB 대기열에 등록
  -> 최대 100번호씩 처리
  -> 요청 접수 / 명시적 거절 / 확인 필요를 즉시 저장
  -> 연결된 접수의 종류별 결과 반영
  -> 기존 접수 화면에서 진행·오류·종료 상태 확인

수신자: 대기 -> 처리 중 -> 요청 접수 | 거절 | 확인 필요 | 제외
작업:   확인 대기 -> 발송 대기 -> 처리 중 -> 완료 | 확인 필요
           +-> 취소 / 확인 만료
```

- 확인 화면에서 접수 ID·전화번호·링크·내용을 서버에 저장. 최종 확인 시 다시 검사하고, 대상의 실제 구성이 바뀌면 수가 같아도 재확인한다.
- 확인 후 신규 접수는 포함하지 않는다. 실제 전송 직전 삭제된 접수는 제외한다. 같은 번호에 유효한 연결 접수가 남아 있으면 그 번호에는 전송한다.
- 번호나 내용이 변경되면 새 번호/내용으로 몰래 바꾸지 않고 제외 사유를 기록한다. 이미 외부로 나간 요청의 취소는 보장하지 않는다.
- DB에 작업, 정규화한 수신 번호, 연결된 선택 접수 ID, 처리 상태, 시각, 오류 분류, 제공사 그룹/메시지 식별자(응답에 있을 때)를 저장한다.
- DB 고유 제약으로 작업+번호 중복 방지. 고정된 종류별 잠금 행 등을 트랜잭션에서 잠가 확인·발송 작업 중복 생성도 방지한다. 단순 조회 후 생성 방식은 사용하지 않는다.
- 미확정 확인 작업은 만료·취소할 수 있다. 확정된 작업의 잠금은 단순 시간 경과로 해제하지 않는다. 처리 종료 확인과 불명확 건 분류 후 종료한다.
- 같은 DB 연결의 database queue를 사용하는 조건에서 대상 확정·발송 작업 등록을 하나의 트랜잭션으로 처리한다. 실제 연결/드라이버를 배포 전 확인하고, 다른 연결이면 기록만 남거나 조기 실행되는 문제를 해결하기 전 기능을 활성화하지 않는다.
- 외부 전송 중에는 DB 잠금을 유지하지 않는다. 전송 전 상태를 원자적으로 선점하고, 결과 저장 때만 짧게 잠근다.
