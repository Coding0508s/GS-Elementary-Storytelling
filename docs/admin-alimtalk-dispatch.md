# 관리자 알림톡 전체 발송

## 최종 전달 결과 조회

- 접수 목록에서 **최종 결과 조회**를 누르거나 화면을 열어두면 30초마다 제공사의 번호별 결과를 조회합니다. 화면 갱신은 5초마다 수행하며 같은 그룹을 30초 이내에 중복 조회하지 않습니다. 한 번에 1개 그룹(최대 100번호)을 확인하므로 여러 그룹은 순차 갱신합니다. 발송 worker가 꺼져 있어도 화면에서 결과 조회는 동작합니다.
- `2000`은 **요청 접수**, `3000`은 **발송 중**, 개별 메시지의 `COMPLETE`와 `4000`이 확인되면 **전달 완료**, 최종 오류는 **전달 실패**로 표시합니다. SMS/LMS/MMS로 전달되면 **문자 전달 완료**로 표시합니다. 전달 완료는 읽음 확인을 의미하지 않습니다.
- 그룹의 `COMPLETE`만으로 전체 성공을 판정하지 않습니다. 대체 발송이 진행 중이면 카카오톡 단계의 실패를 최종 실패로 간주하지 않습니다. 페이지 누락·다른 그룹·모호한 중복 결과·조회 실패는 기존 상태를 유지하고 조회 오류를 표시합니다. 재발송하지 않습니다.
- 예약은 예약 시각 이후부터 최종 결과를 조회합니다. 취소 처리와 충돌하면 취소 상태를 보존하며, 과거 작업의 결과가 최신 작업을 덮어쓰지 않습니다. 같은 번호로 연결된 모든 접수에 결과를 반영합니다. 내역을 숨긴 완료 작업도 최종 결과를 확인합니다.
- 이전 방식의 발송 기록에 제공사 그룹 ID가 없다면 정확한 메시지를 특정할 수 없어 최종 결과를 자동 조회할 수 없습니다. 전화번호만으로 다른 메시지의 성공을 연결하지 않습니다.
- 추가 마이그레이션: `2026_11_03_040000_add_delivery_results_to_alimtalk_recipients.php`. 조회 시각·조회 오류·제공사 상태 코드·전달 채널을 저장합니다.
- 화면을 닫아도 조회하려면 서버의 Laravel 스케줄러를 실행합니다. 로컬에서는 `php artisan schedule:work`, 서버에서는 매분 `php artisan schedule:run`을 호출합니다. 등록된 `alimtalk:sync-results`가 매분 최대 20개 그룹을 조회하며 발송·예약·취소 요청을 하지 않습니다. 수동 조회는 `php artisan alimtalk:sync-results --limit=20`입니다.

규격: [SOLAPI 그룹별 메시지 결과 조회](https://solapi.com/developers/api/msg-groups-getGroupMessageList), [메시지 상태 코드](https://solapi.com/guides/message-status-codes).

## 발송 내역 수정·삭제

- 본인이 만든 내역의 **수정**에서 발송 방식·예약 시간·입장 링크를 바꿀 수 있습니다. 안내 종류는 유지합니다. 개별 선택은 기존 접수자를 유지하고, 등록자 전체 선택은 저장 시점의 등록자로 다시 계산합니다.
- 저장하면 새 확인 화면이 열립니다. 저장만으로 전송하지 않으며, 대상과 내용을 다시 확인하고 확정해야 합니다.
- 대기 중인 작업의 수정·삭제는 이전 작업을 취소합니다. 새 확인 화면은 다른 작업 ID를 사용하므로 예전 대기열 작업이 뒤늦게 실행되어도 다시 보내지 않습니다.
- SOLAPI에 등록된 예약은 먼저 취소합니다. 모든 예약의 취소가 확인되면 수정 화면으로 전환하거나 목록에서 삭제합니다. 일부 취소 실패·응답 불명확 상태에서는 내역을 유지하고 확인을 기다립니다. 상태 새로고침이나 예약 취소로 대조할 수 있습니다.
- 이미 전송이 시작된 작업은 수정할 수 없습니다. 취소 요청 중 전송 시작이 확인된 경우에도 변경 내용을 적용하지 않고 이유를 표시합니다.
- 완료·취소 내역의 **삭제**는 목록에서 숨기는 동작입니다. 원본 발송 결과·제공사 그룹 ID·접수 연결은 감사 기록으로 보존합니다. 이미 전송한 메시지는 취소되지 않습니다.
- 처리 중이거나 결과가 불명확한 작업은 직접 삭제할 수 없습니다. 다른 관리자의 작업도 수정·삭제할 수 없습니다. 오래된 화면에서 중복 저장하면 다시 확인하도록 안내합니다.
- 추가 마이그레이션: `2026_11_03_030000_add_change_management_to_alimtalk_dispatches.php`. 실행 중인 worker는 현재 작업 종료 후 재시작해야 취소 후 변경·삭제 처리가 반영됩니다.

## 일회성 예약 발송

- 오전·입장 안내 각각 **예약 발송 / 즉시 발송**을 선택할 수 있으며 기본은 예약 발송입니다. 예약 시간은 한국 시간으로 입력하며 현재보다 5분 이후여야 합니다. 기존 내역 수정에서는 저장된 방식을 유지합니다.
- 대상 확인 화면에서 시간·대상·링크를 확인하고 **예약 확정**합니다. 명단과 링크는 고정되며 신규 등록·삭제·번호 변경이 이미 외부에 접수한 예약에 자동 반영되지 않습니다.
- 예약 확정 직후 worker가 SOLAPI에 예약을 등록합니다. 모든 번호가 **예약 접수**된 다음에는 로컬 컴퓨터가 꺼져도 SOLAPI에서 발송합니다. 단순히 ‘예약 등록 대기’인 동안에는 worker를 종료하면 안 됩니다.
- 일부 번호가 거절·제외되면 **일부 예약 접수**로 표시합니다. 응답을 잃은 경우 확인 필요로 남기며 자동 재등록하지 않습니다.
- 예약 시간이 지났거나 1분 미만으로 남은 뒤 worker가 실행되면 즉시 발송으로 바꾸지 않고 제외합니다.
- 같은 종류·같은 시간의 중복 예약을 막습니다. 예약 등록이 끝나면 다른 시간 예약이나 즉시 발송은 가능하지만 기존 예약/발송 이력이 있으면 재발송 동의가 필요합니다.
- **예약 취소 요청**은 제공사의 취소 응답을 확인해야 완료됩니다. 이미 발송이 시작되었다면 취소하지 못했다는 사유와 요청 접수 상태를 표시합니다. 통신이 끊기면 취소 확인 필요로 남깁니다.
- **예약 상태 새로고침**은 worker에서 제공사 상태를 조회합니다. 컴퓨터를 꺼둔 동안 발송이 진행됐다면 다시 실행한 뒤 이 버튼으로 확인할 수 있습니다. 취소 처리 중 중단된 작업도 이 버튼으로 대조할 수 있습니다.
- 시간·링크를 변경하려면 취소 완료를 확인한 뒤 새로 예약합니다. 부분 취소·취소 확인 필요 상태를 전체 취소로 간주하지 않습니다.
- 등록 중 또는 미확정한 예약 결과가 남은 작업을 운영 종료 명령으로 닫아도 외부 예약이 취소되지는 않습니다. 알려진 외부 예약이 남아 있으면 종료 명령을 차단합니다.

추가 마이그레이션: `2026_11_03_020000_add_scheduling_to_alimtalk_dispatches.php`.
배포 후 실행 중인 worker를 재시작해야 새 예약·취소 작업이 반영됩니다. 로컬에서는 기존 `php artisan queue:work database`를 종료하고 다시 실행하세요. 새 예약은 전용 작업 클래스를 사용해 구버전 worker가 즉시 전송 경로로 처리하는 것도 방지합니다.

예약 등록은 SDK의 예약 인자를 사용합니다. 취소는 공식 `DELETE /messages/v4/groups/{groupId}/schedule`, 조회는 `GET /messages/v4/groups/{groupId}`를 사용하며 외부 쓰기 요청을 자동 재시도하지 않습니다.

검증에는 한국 시간 전달, 과거·임박 시간 차단, 전체/부분 예약, 취소 응답 불명확, 취소 중 중단 복구, 권한, DB 롤백, 같은 종류·시간 중복 방지, 과거 예약 취소가 최신 즉시 발송 결과를 덮어쓰지 않는 경로를 포함합니다. 실제 SOLAPI 예약·전송·취소는 실행하지 않고 대역으로 검증했습니다.

## 사용 방법

1. 관리자 접수 내역에서 개별 체크하거나 **등록자 전체 선택**을 누릅니다.
2. 오전 안내 또는 입장 안내의 **대상 확인**을 누릅니다. 입장 안내에는 유튜브 링크를 입력합니다.
3. 접수 건수, 고유 수신 번호 수, 번호 오류·중복 통합·이전 요청 이력과 링크를 확인합니다.
4. 이전 요청 이력이 있으면 재발송 동의를 체크한 뒤 **발송 확정**을 누릅니다.
5. 같은 화면의 최근 작업 영역에서 진행 상황을 확인합니다. 화면을 닫아도 서버 작업은 계속됩니다.

전체 선택은 검색 조건·페이지와 무관합니다. 휴지통은 제외하며 같은 번호는 한 번만 전송합니다. 개별 선택은 현재 페이지의 체크한 접수만 포함합니다. 오전·입장 안내의 결과는 각각 유지하며 신청 완료·OTP 발송은 기존 방식을 유지합니다.

확인 화면은 15분간 유효합니다. 대상이나 설정이 바뀌면 다시 선택해야 합니다. 확정 후 신규 접수는 포함하지 않습니다. 전송 전 삭제·정보 변경된 접수는 제외하며 이미 외부로 나간 요청은 취소할 수 없습니다.

## 배포 시 필요한 작업

- `php artisan migrate --force`로 새 저장 구조를 적용합니다. 마이그레이션 전에는 발송 버튼이 비활성화됩니다.
- 기존 worker를 `php artisan queue:restart`로 재시작해 새 작업 클래스를 읽게 합니다. 실제 실행 경로와 프로세스 관리자 설정을 확인합니다.
- 발송은 기본 큐 연결과 무관하게 `database` 연결을 사용합니다. `queue.connections.database.connection`은 앱 DB와 동일해야 합니다.
- 해당 database 연결의 큐 이름(기본 `default`)을 처리하는 worker가 있어야 합니다. 예: `php artisan queue:work database --queue=default`.
- SOLAPI API 키·시크릿·채널·오전/입장 템플릿·발신번호를 확인합니다. 입장 링크 변수 설정도 필요합니다. 기존 대체 문자 설정을 유지합니다.
- 작업별 제한 시간은 60초, 시도 횟수는 1회입니다. SDK 기본 요청 제한은 30초입니다. `retry_after`는 작업 제한보다 충분히 커야 하며 앱은 65초 이하 설정을 거부합니다. 기본값은 90초입니다.
- worker의 PHP CLI에는 `pcntl` 확장이 있어야 작업 제한 시간이 적용됩니다. 이 조건을 운영 환경에서 확인합니다.
- 확인·작업 등록은 같은 DB 트랜잭션에서 수행합니다. `beforeCommit()`으로 jobs 테이블 등록까지 포함하므로 중간 오류 시 함께 롤백됩니다. 별도 queue DB 연결은 사용하지 않습니다.
- 전체 운영 발송 전에 지정한 테스트 번호로 템플릿과 대체 문자 동작을 확인합니다. 개발 검증에서는 실제 발송하지 않았습니다.

## 상태와 중단 복구

- **요청 접수**: 제공사가 요청을 받은 상태이며 실제 수신 완료를 뜻하지 않습니다.
- **예약 중**: 확정한 예약 작업이 등록 대기·등록 중이거나 제공사에 예약 접수된 상태입니다. 참가자 목록에서는 이전 요청 접수 기록보다 현재 예약을 우선 표시하며, 배지에 마우스를 올리면 등록 단계와 한국 시간의 예약 시각을 확인할 수 있습니다.
- 참가자 목록의 발송 결과는 5초마다 갱신합니다. 아직 확정하지 않은 대상 확인과 삭제한 작업은 현재 작업 표시에 포함하지 않으며, 취소 확인 중·확인 필요 상태는 예약 중과 구분합니다.
- **실패**: 명시적인 요청 거절 또는 작업 시작 실패입니다.
- **확인 필요**: 통신 단절, 처리 중 종료, 결과 저장 실패 등으로 접수 여부가 불명확합니다. 자동 재발송하지 않습니다.
- 같은 종류는 확인·발송 중 하나만 허용합니다. 미확정 확인은 취소하거나 만료 후 새로 선택할 수 있습니다.
- 확인 필요 작업은 잠금을 유지합니다. 지연된 작업도 시간만 지났다고 잠금을 풀지 않습니다.

작업이 중단되었거나 확인 필요로 끝나면 운영자가 해당 worker와 외부 요청의 종료, SOLAPI 발송 기록을 확인합니다. 작업 ID·번호별 처리 시각과 제공사 그룹 ID를 대조합니다. 응답 후 DB 저장이 실패한 경우 애플리케이션 로그의 `관리자 알림톡 요청 응답`에서 작업 ID와 그룹 ID를 찾을 수 있습니다. 이 로그에는 수신 전화번호를 기록하지 않습니다.

종료를 확인한 다음에만 아래 명령을 실행합니다.

```sh
php artisan alimtalk:close <작업UUID> --confirmed-stopped
```

이 명령은 처리 중인 번호를 확인 필요, 아직 대기 중인 번호를 제외로 남기고 같은 종류의 잠금을 해제합니다. 메시지를 다시 보내지는 않습니다. 살아 있는 worker나 외부 요청이 남아 있는 상태에서 실행하면 중복 발송 위험이 있으므로 먼저 종료를 확인해야 합니다.

## 검증

```sh
php vendor/bin/phpunit --filter='AdminAlimtalkDispatchTest|ResetReceiptNumberTest|SolapiAlimtalkServiceTest|SolapiSmsServiceTest|SeminarPresentationTest'
```

SQLite 검증과 별도로 격리한 MySQL 테스트 DB에서 `AdminAlimtalkDispatchTest`와 `ResetReceiptNumberTest`를 실행했습니다. MySQL 동시성 테스트는 `pcntl_fork`로 독립 연결 두 개를 사용해 같은 종류의 생성·확정 중복 방지와 다른 종류 결과의 동시 병합을 검증합니다. SQLite 실행에서는 이 테스트만 명시적으로 건너뜁니다.

브라우저에서는 25건 중 중복·번호 오류를 제외한 23번호 확인·확정·모의 전송·진행 갱신, 현재 페이지 선택/해제, 검색 결과가 0명인 상태의 전체 선택, 입장 링크 확인·취소를 검증했습니다. 좁은 화면에서도 새 영역의 가로 넘침을 확인했습니다.

테스트 범위에는 100/101 및 1,001번호, 두 번째 작업 등록 실패 시 이미 등록한 첫 작업까지 롤백, 제공사 접수 후 결과 저장 실패, 작업 재실행·강제 중단 상태, 설정/대상 변경, 재발송 동의, 권한·세션 만료와 마이그레이션 되돌리기가 포함됩니다.

전체 테스트에는 변경하지 않은 홈 화면 기본 테스트(`tests/Feature/ExampleTest.php`)가 세션 테이블 미구성으로 실패하는 기존 문제가 있습니다. `config/session.php`가 database 드라이버를 고정하고 해당 테스트가 세션 테이블을 만들지 않기 때문입니다. 이번 기능 테스트는 별도의 격리된 세션 설정을 사용합니다. PHP 8.5에서는 기존 Laravel/설정의 사용 중단 경고도 발생합니다.
